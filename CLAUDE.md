# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

zeroskip is an append-only ordered key-value store: a directory of immutable and append-only files, with lock-free readers and a single writer. It's a C library (libzeroskip) with a CLI tool (zstool), a test suite (zstest) and a benchmark tool (zsbench).

Its sibling library `twom` (`../twom/`) is a mutable single-file skiplist. zeroskip suits workloads that are append-heavy, want readers that never take a lock, and tolerate compaction happening out of band.

**The spec is normative.** `doc/specification.md` specifies the on-disk format, the database layout, the concurrency and durability protocol, and recovery, so that independent implementations in different languages interoperate on the same database concurrently. Requirements are labelled (`F-n` format, `D-n` database, `C-n` concurrency, `R-n` recovery, `A-n` API, `G-n` guarantee, `T-n` tests); **MUST** and **MUST NOT** are normative. When code and spec disagree, the spec wins — or the spec gets changed deliberately, in its own commit.

`doc/implementation-plan.md` is the implementation plan.

## Build Commands

```bash
make                # libzeroskip.a, libzeroskip.so/.dylib, zstool, zstest, zsbench
make check          # run the test suite (alias: make test); includes stdcheck
make stdcheck       # every source compiles clean at -std=c11 and -std=c17
./zstest            # run all tests directly
./zstest record     # run tests matching a substring filter
make asan           # rebuild under ASan + UBSan and run the suite
make leaks          # rebuild plain and leak-check (LSan on Linux, leaks(1) on macOS)
make mutate         # verify the suite can actually fail (see Testing below)
make corpus         # regenerate the golden corpus (see below before using)
make bench          # zsbench --selftest, then a small smoke benchmark
make clean
```

Requires: C99 compiler, POSIX (`mmap`, `fcntl` locking, `/dev/urandom`). Builds on Linux, macOS and the BSDs with no external libraries.

**C99 is the target and should stay the target.** `zeroskip.c` is *vendored* into other projects, so whatever standard it requires, every host build has to meet — the same papercut as requiring a feature macro the host does not set, which is exactly how a downstream Linux build broke on `_GNU_SOURCE` (`PATH_MAX`, `strdup`, `nanosleep`, `realpath` and `fdatasync` all vanish at once, and every error points at `zeroskip.c` rather than at the missing `-D`). Nothing in the code is written around a missing C11/C17 feature: `_Static_assert` would assert nothing real here, because the on-disk layout is deliberately not struct layout (G-0 — encode and decode go through explicit `memcpy` at literal offsets, so `sizeof`/`offsetof` describe nothing a file depends on, and the real hazard of an encoder and decoder agreeing on a *wrong* layout is only catchable by `test_header_byte_layout`'s byte literals). C11 atomics are optional (`__STDC_NO_ATOMICS__`), so the C-1j registry would keep its `__atomic_*` fallback either way. `make stdcheck` guards the other direction — a consumer *building* at a newer standard — and runs inside `make check` at about a third of a second.

**The `-Werror` gate is a Linux gate, and it needs gcc.** `zeroskip.c` is vendored into Cyrus, which builds `-Werror`, and clang finds none of what gcc finds here: on Debian Trixie (gcc 14, clang 19) the library and both tools were clean under clang while gcc reported seven warnings in the test binaries — six `-Wformat-truncation` on `snprintf("%s/%s", dbdir, name)` into a `PATH_MAX` buffer (gcc checks the *declared* bounds, and `dbdir` is itself `PATH_MAX`; hence `DBPATH_MAX` in `zstest-crash.c`), and one `-Wstringop-overread` reading "16 bytes from a region of size 0", which is how gcc words a possibly-NULL pointer — a test reaching into `db->uuid` after a reopen it never asserted non-null. Both fixes state the bound or the precondition rather than suppressing. Run it in a container over a copy of the tracked files, both compilers:

```bash
git ls-files -z | tar -czf /tmp/src.tgz --null -T -   # never mount the checkout: make clean would eat the host build
docker run --rm -v /tmp/src:/src -w /src debian:trixie \
    bash -c 'apt-get -qq update && apt-get -qq install -y build-essential clang &&
             for cc in gcc clang; do make clean; make CC=$cc EXTRA_CFLAGS=-Werror check; done'
```

Default `CFLAGS` are `-Wall -Wextra -g -O2 -fno-strict-aliasing -std=c99`. Append to them with `EXTRA_CFLAGS=...` rather than overriding `CFLAGS`, which would drop the platform feature defines.

**Every target builds a binary called `zstest`**, so make cannot tell an instrumented build from a plain one and will reuse whichever was built last. `asan` and `leaks` therefore clean first, and you should assume `make check` straight after `make asan` is running the *sanitizer* binary. This is not hypothetical: it made `make leaks` fail with "malloc replacement library without the required support", which reads like a tooling problem and was really ASan's `malloc` in a stale binary. `-fno-strict-aliasing` is precautionary rather than known to be required: the little-endian accessors go through `memcpy`, so unlike `twom.c` they do not punt on aliasing.

## Architecture

**Two file kinds, distinguishable from the header alone.** `end == 0` means an *unordered* file: one generation, records in append order, no pointer section. `end != 0` means an *in-order* file: a range of generations, records in key order, with a pointer section. A reader always knows, before reading anything else, whether a pointer section must be present.

**The directory is the file set.** There is no manifest. Filenames carry each file's generation range, so one `readdir` yields the set and every range without opening a file. Overlapping files are *resolved*, not rejected (D-5).

**Nothing is ever mutated.** Files are only appended to or created. A new file is published by `rename`. Every index is private to the process that built it. Nothing needs cleaning up when a process dies.

**Sections in `zeroskip.c`**, in dependency order — each may only call downwards into those above it:

```
TUNING              constants, limits
LIBRARY SUPPORT     zmalloc, random bytes, UUID, LE load/store, overflow guards
COMPARATORS         F-11a total order
CHECKSUMS           three engines
FILENAMES           D-0/D-1 format and parse
FILE HEADER         72-byte header
RECORDS             10 type bytes, terminators
FILE OBJECT         open, mmap, kind detection, the one bounds-checked accessor
UNORDERED FILE      span chain replay, complete-at
POINTER SECTION     section + trailer, binary search  (needs an open file)
PRIVATE INDEX       base+delta ordered index
POINTER TABLE CACHE spec section 8: load, publish, sweep
PER-FILE CURSOR     uniform seek/next over both kinds
FILE SET            readdir, D-5 resolution, D-6 tiling
SNAPSHOT            C-4 protocol
FILE LOCKING        three fcntl byte locks + the C-1j same-process registry
READ PATH           D-14 lookup, D-14e merge cursor
WRITE PATH          spans, commit, two durability gates
CONVERSION          unordered -> in-order
REPACK              selection and merge
CONSISTENCY         F-28, F-26f, dump
OPEN AND CLOSE      open is recovery
PUBLIC API          the three entry-point forms
```

**Naming conventions:**
- Public API: `zs_db_*`, `zs_txn_*`, `zs_cursor_*`
- Internal types and functions: `zsi_` prefix, all `static`
- Macros: UPPERCASE

**Error handling:** every function returns `enum zs_ret` (`ZS_OK = 0`, `ZS_DONE = 1`, negatives for errors). Output through pointer parameters.

## Things that look like bugs and are not

Each of these has cost someone an afternoon. They are load-bearing.

- **`zsi_csum_xxhash` does not short-circuit on empty input**, unlike twom's equivalent. F-26g requires the engine's value for empty input, and a zero-record in-order file depends on it.
- **Every comparison goes through `zsi_cmp`, which takes the BUILT-IN comparator by a direct call.** `zs_compar` is a function pointer, so a comparison was an indirect call — uninlinable, and comparable in cost to the tiny body it invokes. The test is pointer equality against a static symbol and is perfectly predicted, since a database's comparator is fixed at open; what it buys is not the branch but the inlining the branch enables. A caller-supplied comparator keeps the indirect path. Both arms run the same function, so F-11a's order is untouched and this is not interoperability surface. The checksum engine is the *other* pointer the merge calls indirectly and is deliberately NOT specialised: XXH3 over a record is real work (~8% of a scan), so the call is a small fraction of it, where the comparator's call was a large fraction.
- **The default comparator compares through `memcmp`, and orders by length when the common prefix is equal** (F-11a). `memcmp` is *defined* to compare as unsigned char, which is exactly the prefix rule and states the platform requirement rather than re-implementing it; a hand-rolled loop over plain `char` misorders every key above `0x7F` on x86 and not on ARM. Only its **sign** may be used — the magnitude is unspecified — so it is normalised to -1/0/1. It was a byte-at-a-time loop until 2026-08-15; `compar: byte-at-a-time prefix` is that version, kept as an `equivalent` mutant. `memcmp` alone is not enough — it says nothing about keys of differing length, so a key and its own prefix come out wrong, which is what the length tie-break exists for and what `compar: longer key first` preserves.
- **`zsi_type_valid` is a `switch`, not a bit-property computation.** F-12's table is normative; a computed predicate is a second specification that can drift.
- **Records carry no back-reference, and a repack DERIVES tombstone retention** (F-18, D-19, since 2026-08-15). Every record used to carry an *ancestor* — the generation holding the key's previous version — computed by `zsi_ancestor_for`, which searched the whole file set for the key on **every store**, creates included (those miss everywhere, so no early exit). It was then read only by a repack. Measured at ~0.09µs per file in the set per store: nearly double the store cost at 4 files, ~9µs at the 103 files seen in the field. `zsbench`'s `store into N files` lines exist to keep that visible, and no store workload could see it before, because they all start from an empty directory. The general shape: **store a derived fact only when deriving it is expensive at the moment it is needed** — here it was cheap then and expensive when recorded, because the two moments differ in frequency by orders of magnitude.
- **A tombstone is retained iff the newest record for its key BELOW the output range is a value** (D-19). Not "is present": the search stops at the first file holding the key either way, so knowing whether that record is a value or a deletion is free, and a deletion below already hides everything under it. Files *above* the range cannot enter the test — a newer record shadows everything below it, so a newer file can only make a retained tombstone redundant, never make a dropped one unsafe. That asymmetry is the whole reason the test looks one way, and `test_repack_d19_newer_file_recreates` is the case that would expose it if the reasoning were inverted.
- **Repack writes a record even when a newer file already shadows the key.** Being shadowed does not permit dropping it; only D-19 does. That is now a *cost* argument, not a correctness one: proving a newer file shadows a key needs a lookup per KEY, where D-19's test needs one per surviving tombstone (D-19a).
- **A conversion keeps every tombstone unconditionally, and must.** Its output covers its input's range (D-5a), so there is nothing below it to reason about. D-19 belongs to repack, which merges a *range* and can look under it. Compaction needs no special case either: it spans everything, so nothing is below and every tombstone goes.
- **Bit `0x08` is reserved, not reused, and the surviving type bytes kept their values.** That is why removing the four `*_ANC` forms changed *no* golden corpus byte — and why the corpus never covered the case that mattered. Every pre-existing case writes into the generation it created, so none ever produced an ancestor record; `tests/corpus/cross-generation-update` was added to cover the update-and-delete-across-generations shape, which is now the byte-level statement of F-18.
- **A failed `fdatasync` is never retried.** A second call can succeed after the dirty pages were discarded, so treating success as proof of durability is wrong (C-7a).
- **`ZS_NOSYNC` skips the two commit gates and nothing else.** The structural syncs — the new active file's header, conversion and repack outputs before their publishing rename, and C-6's directory syncs — run in every durability mode, because they are integrity, not durability (C-6b). Re-adding a `!db->nosync` guard at one of them "for consistency" is how a NOSYNC crash loses *converted generations* instead of the active tail: the rename publishes a possibly-torn file and entitles retiring the inputs that were the records' only complete copy. It shipped that way until 2026-08-13. `crash/nosync_structural_syncs` pins each structural operation's exact sync signature; the loss bound NOSYNC actually offers — a valid prefix of the active generation, on top of everything published — is sqlite WAL/NORMAL's shape, with `zs_db_sync` as the caller's durability point.
- **The active file is `zeroskip-<uuid>.current` and its generation is in the HEADER, not the name** (D-1b). The dot is load-bearing twice: `zeroskip-<uuid>-*` then matches the generation-named files and only those, and `.` (0x2E) sorts above `-` (0x2D) so it still comes last. What it buys is C-4i — freshness is now ONE `stat` of a fixed path (size for an append, inode for a rollover) instead of a `getdents` sweep per transaction, which on a VFS-over-ZFS mount cost about what the `fdatasync`es cost. The reasoning that makes one file sufficient: **a rename never makes committed data visible that was not already visible**, so conversions, repack outputs and D-23 removals are invisible here and harmless, and a vanished file is caught lazily by an `open` failing into C-4b's retry.
- **Inferring the active file's generation is wrong in the conversion window.** D-5 renames the output in *before* removing the input, so for that moment the active file is SUPERSEDED, not new — its records have just been published as an in-order file and its real generation is the one that file covers. "One above the highest" puts it a generation too high, D-23a's same-highest check then refuses to remove it, and the writer cannot create its replacement because the name is still taken. Symptom is `ZS_IOERROR` on every rollover. Read the header.
- **D-5a's ordering is a comparison now, not a naming accident.** It used to come free from name collation, because the active file's name was a strict prefix of the in-order name for its generation. `.current` carries no generation, so a name sort puts it after *every* in-order file — which in the conversion window would pick the superseded file over the one that just replaced it. `zsi_entry_resolve_order` sorts by generation, then reach, then unordered-before-in-order. **The scan itself leaves the entries in `readdir` order**, deliberately: resolution and salvage each impose the order that means something to them, and the lexical name sort that used to be there became dead code the moment D-1b landed — its two mutants had quietly gone NOT CAUGHT, which reads as a test gap and was really a mutant guarding nothing.
- **An invalid-header active file does not participate in the set, but still occupies the name.** It has no discoverable generation (D-1b) and no recoverable record (D-10), so it is dropped from the scan — but it is still on disk, so `zsi_create_active` has to reclaim the name. It refuses to if the header is VALID: that means a caller skipped D-12b's convert-first, and destroying records is not a recovery. The open probe uses `zsi_fileset_scan_raw` for the same reason — a file whose header did not survive still proves the database exists, and dropping it would make a crash during the first header write produce a database only `ZS_CREATE` could open (G-3).
- **Salvage uses `zsi_fileset_scan_raw`, and sorts a start-0 entry LAST.** The filling scan drops an unreadable active file, which is often exactly the file salvage was called to rescue. And with the generation unknown, a naive sort puts it first — inverting S-10's oldest-first scan, on which the possibly-stale report depends.
- **The lock file is never unlinked**, and `flock` is never used. Both silently break mutual exclusion (D-3b, C-1e).
- **There is no in-process mutex, and adding one would still be a regression — but two handles in one process DO exclude each other now** (C-1j, since 2026-08-14). The distinction is what you key on. A per-handle mutex is two different objects, so it excludes only threads *sharing a handle*, which is not what G-5 reads as promising; an earlier version had one, and two threads with separate handles overlapped 398 times in the write section. C-1j keys on the *database* instead: `F_OFD_SETLK` where the platform has it (Linux, macOS — the kernel scopes the lock to an open file description, so it costs nothing), and a process-global registry keyed on the lock file's `st_dev`/`st_ino` elsewhere. Both are taken *together with* the `fcntl` lock, never instead of it — the registry is invisible outside the process, and the `fcntl` lock is what a peer implementation sees (C-1e). **Handles are still not thread-safe**: two threads on one handle remain the caller's problem.
- **The registry's spinlock is a compiler builtin, not a pthread mutex**, and `test_lock_no_thread_machinery` greps for `pthread_` to keep it that way. It guards the list and the `held` words only, and is never held across the `fcntl` call, which can block for as long as another process wants. The blocking wait is a 1ms poll for the same reason: a condvar needs the thread library this file does not link, and two handles contending inside one process was a caller error until C-1j, so it is the rare path rather than the hot one.
- **`zsi_lock_registry` is a variable, not an `#if`,** so `test_lock_two_handles_one_process` runs T-14 against *both* C-1j mechanisms. Every platform anyone develops on has `F_OFD_SETLK`, so the registry would otherwise be dead code in a concurrency path, discovered by the one platform that depends on it. When the registry is forced on, `zsi_lock_fcntl` deliberately drops back to `F_SETLK`: leaving OFD in place would exclude the two handles anyway and the registry path would be testing nothing.
- **A cursor from `zs_db_begin_cursor` without `ZS_SHARED` holds the WRITE LOCK for its whole lifetime**, because it opens an implicit write transaction. Since C-1j that blocks other handles in the same process, not just other processes. `test_cursor_live_sees_other_handle_commit` was written without it and passed only because same-process handles excluded each other by nothing — against a second *process* it would always have deadlocked. A read-only traversal wants `ZS_SHARED`.
- **The terminator checksum, not a lock, is what makes reading a live file safe** (C-4f). It covers the span *and* the terminator, so a terminator whose data has not landed reads as absent.
- **Appending uses the ACTIVE FILE's checksum engine, not the handle's.** A `ZS_CSUM_*` flag chooses the engine for files a handle *creates* and never overrides what an existing file records (A-6, F-5a). Using the handle's engine to checksum a span appended to a file recording a different one is silent data loss: the terminator validates under neither, so the next reader rejects the whole span (F-22 doing its job) and every record in it vanishes. Found by the corpus's engine-0 case, because that case is built by separate `zstool` invocations and so the second one had a different default.
- **The writer STREAMS: records hit the active file at `zs_txn_store`, not at commit** (C-8's shape, since 2026-08-12; it buffered before that). Transaction memory is O(keys) — the pending array is a key→offset index, values live in the file and read back through a per-transaction list of mappings that each at least double and are unmapped only when the transaction ends (that list IS the A-4 mechanism; unmapping a superseded one "to save address space" dangles every pointer already returned). An abort appends a ROLLBACK terminator with **no sync** — the next commit's own gate 1 orders it (C-8a) — so a span now records the transaction's *history*, and `store k` + `delete k` is two records, shadowed by offset order (D-17b), not one. A failed stream **poisons** the transaction: commit refuses and voids the span like an abort, because a COMMIT terminator over a torn record makes replay complete the file at the tear (F-24) and lose the whole span.
- **A transaction lookup decides the match from the PENDING ARRAY's key, and materialises the record only on a hit.** `zsi_fcur_seek` ends in `zsi_fcur_load`, so seeking and then comparing the decoded key — which is what `zsi_fcur_find` did until 2026-08-14 — makes a **miss** cost a `write(2)`: the seek lands on the neighbouring pending record, decoding it flushes the writer's chunk through `zsi_txn_at`, and the record is then thrown away as not equal. `zsi_pend_set` already records the key beside the offset, so the test needs no bytes at all. This matters because *probe-then-insert is the layered-consumer shape* — a caller checking whether a key exists before storing it misses every time — and it is invisible to any store-only benchmark: found only when the sqlite integration reported 300k `write()` against 10 `fdatasync` over 100k rows in ONE transaction, and `zsbench` at the time had no workload that read inside a write transaction at all. `zsi_txn_cur_at` exists so the peek and the load cannot disagree about *where* the cursor is; split them and a lookup answers for one record while positioning on another. The two halves are complementary and both are needed: this covers reads that MISS, `ZS_EPHEMERAL` covers reads that HIT.
- **`ZS_IFCHANGED` is a caller's optimisation, and deliberately not the implementation's** (A-1d). Skipping a redundant write costs a point lookup — the same one removed with the ancestor — so doing it unconditionally would hand back exactly what that change bought. It shares the `ZS_IFEXIST`/`ZS_IFNOTEXIST` probe, and `zsi_lookup` folding a tombstone into `ZS_NOTFOUND` is what makes `rc` alone answer both halves: NOTFOUND means absent *or* deleted, ZS_OK means a live value. Comparing value bytes and lengths alone would be wrong — an empty value and a deletion are both zero bytes and are distinct states (A-1). The skip must not bump `pend_seq`, or every cursor on the transaction refreshes for a write that did not happen; that is harmless for correctness, so it needs a mutant rather than a data test. Its structural payoff is on deletes: without it, deleting an absent key writes a tombstone for a key that never existed, which a repack then carries until it can prove the key absent below it.
- **`ZS_EPHEMERAL` serves a read out of the chunk buffer, and that is only sound because a record never straddles the boundary.** `zsi_txn_append` flushes and then copies the record in whole, or writes it straight through when it is too big for the chunk at all — so a range at or above `flushed` is either wholly buffered or wholly past `wsize`, which the bounds check already rejected. The partly-below case cannot arise, which is why there is no code for it; if appending ever learns to split a record, this branch returns half a record and the decode reads adjacent bytes as a length. The flag is **rejected**, not ignored, on the public cursor and `foreach` forms (A-4b): those yield across steps, and `zs_db_begin_cursor` rejects it *before* its begin, which would otherwise take the write lock for a call already known to fail. Conditional stores (`ZS_IFNOTEXIST`/`ZS_IFEXIST`) take it internally whether the caller asked or not — the probe wants the answer and discards the record. What it is worth: 0.274s to 0.074s over 100k store-then-fetch-back pairs, against 0.063s for the stores alone.
- **`nspans` counts spans in the REPLAY WINDOW, not in the file** (D-9d), and **the D-13b commit fold has to increment it by hand.** The window is what a rebuild actually walks — from `cached_upto`, where a table-seeded reader would start — so it resets at the top of the walk and at a successful publication, and a configured cache makes `rollover_txns` quiet rather than making it fire on a file's lifetime total. The hand-carry is the trap, and it is the same one `last_term_off` sits in: the fold exists to *skip* the replay, so nothing else advances the count. Drop it and a sole writer — which takes that branch at every commit, and is exactly the no-cache shape with an unbounded rebuild — leaves the count wherever the last rebuild left it, so the bound never fires for the only writer it was written for while every byte-threshold test still passes. `zsi_active_full` is one predicate for four sites (rollover, the repack cascade's new-generation probe, D-25d's seal, the oversized fallback) because they must agree; teach the byte half to only some of them and the writer oscillates, sealing a file `zsi_writer_active` then goes on appending to.
- **The terminator checksum re-reads the streamed span through the mapping.** C-4f's checksum covers the span's bytes plus the terminator, and the engine API is one-shot (engine 2 is the caller's, so no incremental variant is possible). One warm pass at terminator time; the buffered writer paid the same pass over RAM. A ROLLBACK's checksum matters as much as a COMMIT's — an invalid rolled-back span completes the file early (F-24).
- **Record checksums (F-32) are not verified during replay or pointer-section load**, only at materialization — the lookup return and the cursor yield. Span checksums are the mirror image: verified at replay in EVERY mode, `ZS_NOCSUM` included, because **verification rides indexing** (F-5e, since 2026-08-14) — a NOCSUM reopen after a crash under relaxed durability would otherwise accept a terminator whose data never landed and surface garbage as committed records. NOCSUM means exactly one thing: skip the F-32a check at materialization. There is no `nocsum` parameter anywhere in the replay/index chain anymore; re-plumbing one in is the regression, and the bit-4 table gate (`idx: accepts an unverified table`) inverts with it. Verifying in replay looks like defence in depth and is a data-loss bug: F-24 completes a file at its first invalid record, so a verifying replay turns one flipped value byte into the silent loss of every record after it. The span checksum guards structure and liveness (C-4f); the record checksum guards the bytes a caller is about to consume. And they answer different questions in salvage too: a record checksum proves bytes, a terminator proves the transaction was *committed* (S-8), so salvage's span walk deliberately ignores record checksums while its in-order walk — where publication by rename implies commitment (D-21) — trusts them per record. `test_record_csum_replay_no_truncate` holds the read half apart; `test_salvage_unverified_needs_the_flag` the salvage half.
- **Decoding accepts non-canonical records and terminators; it does not reject them.** A big form whose lengths would have fitted the short form is something a conforming writer never produces (F-15) — but rejecting it on read would be a *data-loss* bug. (The space of non-canonical records shrank with the ancestor: it used to include a record storing an ancestor equal to its own file's `start`, which decoded identically either way and so could *only* be caught by a canonicality check.) A record that fails to validate makes an unordered file complete at that point (F-24), discarding everything after it, and G-3 forbids corruption costing committed data. So a peer with a canonicalisation bug would silently cost us every record it wrote after its first non-canonical one. `zsi_rec_is_canonical` / `zsi_term_is_canonical` exist so `zs_db_check_consistency` reports the divergence while still reading the data, which is the precedent T-6 sets explicitly.
- **A pointer table is checksummed with the DATA FILE's engine, not the handle's.** Same rule as appending, same reason (P-7, A-6, F-5a): a table checksummed under the handle's engine validates for nobody, so every reader silently rejects it and the cache does nothing while appearing to work.
- **Every pointer-table rejection is `ZS_NOTFOUND`, not an error.** A table is an optimisation in a directory the database does not depend on. Reporting a corrupt one as corruption would let a file outside the database make a readable database look unreadable, which is the opposite of G-3.
- **A pointer table is never `fsync`ed** (P-14). It is rebuildable and self-validating, and syncing it would put a third sync on a commit path C-7 defines as two.
- **`zsi_index_flatten` does not merge the delta in place**, though that would be cheaper and would compact the index as a side effect. An index may be shared with a live `struct zsi_index_cur` holding positions into *both* arrays, and rewriting them underneath it is exactly the in-place mutation G-6 forbids.
- **`term_off` in a pointer table is not redundant with `valid_upto`.** Terminators are located by scanning forward (F-20), so a reader given only `valid_upto` cannot find the terminator below it without performing the very replay the table exists to avoid.
- **A write begin runs the C-4i probe; it does not rebuild the snapshot.** "Refresh to be safe" is not safer — the probe is exact (every commit either grows the active file or renames), and the sole writer's own commit already left `db->snap` current via the D-13b fold, so an unconditional rebuild re-derives a snapshot the handle holds, at O(active file) per commit. That was the shipped behaviour until 2026-08-13, found downstream as a throughput sawtooth: single-record commits decayed from ~6000/s on a fresh active file to ~800/s near 2MB, snapping back at every rollover. `test_write_begin_reuses_snapshot` pins the old snapshot and asserts identity across a begin.
- **The publish threshold's expensive end depends on WHO REBUILDS**, and measuring it with the wrong shape gets it backwards — it happened in both directions. The replay from the last published point is paid per snapshot rebuild: at open, and at a begin that follows another process's commit. Writers alternating across processes rebuild every begin, so their expensive end is the HIGH one (16000 single-store transactions: 13.2s no cache vs 2.0s at 32KB, rebuild forced per begin). A sole writer rebuilds nothing in steady state, so its only cost is republication — the LOW end — and no cache at all is its fastest write configuration. The 32KB default sits in the knee of the rebuilding shape, the one the threshold exists to bound; `doc/benchmarking.md` has both curves.

- **A commit that grows the active file past rollover_size seals it itself** (D-25d), so the steady state is AT MOST one unordered file — zero right after a crossing commit — and a one-transaction bulk load ends with an in-order file. The start-of-commit rollover check still exists and is not dead: it recovers oversized actives a crash or a non-sealing peer left behind, and is the fallback when a seal fails. The sealing commit also skips the P-13 table publish (D-25e); publishing there is not a bug a test can see — the seal's own refresh sweeps the table — but it writes and deletes a whole table for nothing, megabytes on a bulk load.
- **The commit-site incremental fold requires `refcount == 2`, and 2 is correct.** db->snap and txn->snap both reference the snapshot at that point, so two references mean "nobody else" — a cursor makes it three and forces the refresh fallback (G-6). It was `== 1` from the first commit, which made the branch dead code and every commit a double rebuild; a mutant that could not be caught found it. Do not "simplify" the count.
- **A read-only handle never creates `zeroskip.cache`, only uses one already present** (P-2b, R-3). Creating a directory inside the database on a read-only open is a visible side effect on a forensic copy or read-only mount. The per-uuid level under a configured root is different: ANY handle may create it, because it is outside the database.
- **Sealing converts the active file in place rather than rolling over first.** A conversion output covers its input's range (D-5a), so the newest file becomes in-order and there is simply no active file until the next write. Rolling over first reaches the same layout while consuming a generation per seal, and generations are finite (D-9c). `test_seal_creates_no_new_generation` is the only thing that tells the two apart.
- **Repack SELECTION is not normative, and the rule is "merge from the oldest file the newer ones collectively outweigh"** (D-16). Any contiguous run is a valid repack — a peer that never repacks is conforming, just slow — so only adjacency and the merge semantics (D-17 to D-23) are requirements. The invariant this policy leaves is that every file is at least as large as the sum of all newer ones, so sizes fall at least geometrically and the file count is bounded by log(total/smallest). **Comparing against the SUM is the whole point**: a rule comparing each file with its immediate *neighbour* stalls on an irregular tail — 100, 60, 50 merges nothing, because 50 < 60 stops it at the first step even though the two newer files together outweigh the oldest, and deletions and dropped tombstones produce exactly those sizes. The comparison is **strict** for the same reason: the left side is a sum, so two equal files wait and a third collapses all three. (A neighbour-comparing rule needs the opposite — it must merge equals or it never merges at all, since rollover produces near-identical sizes. Same-looking test, opposite conclusion.) Measured against the pairwise rule: 4 files → 3 on `fetch` (+7%), 3 → 2 on `store, one txn each` at the same 1.2× write amplification.
- **The cap on top of that (A-16, `repack_max_size`, default 512MB) skips the LEADING oversized files, and it has to yield or it destroys the bound above.** Bounding what one merge rewrites is easy; the thing that is not obvious is what it costs. A skipped file is never selected again, so the file count stops being log(total/smallest) and grows *linearly* in total size — which is the 103-file field case, the read path degrading linearly (D-14d). Zeroskip cannot do what an LSM does about this, because the file set is partitioned by **generation** (D-6 tiling), not by key: there is no "split the big level by key range" available, so a bigger file count is directly a wider merge on every scan and every missing-key lookup. Hence `ZSI_REPACK_MAX_FROZEN`: past 8 skipped files the cap yields for that selection and the uncapped walk merges the pile, which is the same doubling-amortised work the uncapped policy would have done anyway. Steady state unchanged, repacks in between cheaper. **The budget counts SKIPPED files, not all in-order files** — the natural ladder is log(total/`rollover_size`) deep, about 15 at 100GB, so a budget over the total would hold a large database permanently in the uncapped case and the cap would never act at all. Two more traps: only the LEADING run is skipped (excluding an oversized file in the *middle* makes the inputs non-contiguous, which D-19 and D-6 both rest on), and the sum is accumulated over the **surviving** range (weighing skipped bytes as if they sat above the candidate merges files the rule should have left alone, and is invisible on any layout where the skipped side is small — `test_repack_max_size`'s third case exists only because writing the mutant found it). 8 is a guess, not a measurement: `zsbench` has no workload that builds a file set this deep at these sizes.
- **The corpus is generated and replayed with `ZS_NOAUTOREPACK`** — `tests/gencorpus.sh` passes `--noautorepack` and the replayer sets the flag. Selection is not normative, so a case that let the cascade fire would pin *this* implementation's policy into golden bytes, and a peer with a different policy would read a spurious diff. Cases that want a merge say so with an explicit `op repack`; `repacked` and `empty-inorder` both do, and `empty-inorder`'s second generation is deliberately the larger one so that the merge is selected at all.
- **A write transaction runs the repack cascade at BEGIN, and only when it is about to start a new generation** (D-16e). Not at the end of the commit that created the work: C-1d orders repack before write, and a commit holds the write lock for its whole life, so it structurally cannot take the repack lock. At begin nothing is held. The trigger is D-9a's condition — no clean active file, or one past `rollover_size` — because that is the only way the file count grows; broadening it to every begin is *not* a harmless tuning change, it merges at moments the narrow trigger leaves alone. `test_autorepack_only_at_a_new_generation` is what catches that, and it exists because nothing did until 2026-08-14: the other two D-16e tests use store-seal-repeat, which leaves no active file, so every begin starts a generation and the narrow rule and "every begin" agree on the whole workload. Seeing the difference needs work pending *and* a clean active file with room — and that test deliberately leaves the cascade armed, the one documented exception to setting `ZS_NOAUTOREPACK` on a layout test, because the armed cascade declining to fire is the subject. Both tests read a possibly-stale snapshot on purpose; `zsi_repack` refreshes and re-selects under the repack lock, so losing the race costs one lock acquisition. Before this, nothing in the library ever acted on `zs_db_should_repack` — a caller who did not know to call it accumulated files forever, seen in the field at 103 files with fetch 17.5x slower than merged, presenting as "the database is slow". `ZS_NOAUTOREPACK` (A-14) exists because the cascade is unbounded (D-16b): mean cost improved but the worst case went 1369µs to 5286µs. **Any test whose subject is a file LAYOUT must set it**, or the cascade merges the layout away before the assertion — that is why `fresh_db_noautorepack`, `zstool --noautorepack` and one `open_db(ZS_NOAUTOREPACK)` in `zstest-crash` exist.
- **Compaction takes the repack lock and then the write lock** (C-1d), which required *amending* C-1d: it previously said nothing holds both. The locks are now one chain, repack → write → remove, and the assertion in `zsi_lock_take` enforces it — it fired the first time compaction ran, because the spec had been amended without the code following.
- **Compaction merges every maximal RUN of adjacent in-order files, not the in-order prefix** (D-26b). Size-based selection does not apply to it, but adjacency (D-16, D-19) still does, so a file nothing can convert splits the set. Taking only the prefix merges *nothing at all* when such a file sits second — exactly the damaged database where "best effort" has to mean something.
- **`zsi_repack_run` is the single merge entry point.** Both `zsi_repack` and `zsi_compact` go through it so D-17 to D-23 are implemented once. A second call site for `zsi_repack_merge` is how two sets of retention rules would drift apart, and D-19's tombstone rule is the one nobody would notice diverging.
- **The fileset scan copies `d_name` with an explicit length, not `snprintf`.** `zsi_name_parse` has already bounded the name at 63 characters, but the compiler cannot see that and `d_name` is a declared `char[NAME_MAX]`, so `-Wformat-truncation` fires — and Cyrus builds `-Werror`. The explicit copy states the bound where it is relied on instead of suppressing the warning.

- **Salvage does not share the read path, and must not.** It exists to read what §5 and §7 refuse — a set that does not tile, a header that fails, a pointer section that will not load, spans after a bad one. Routing it through `zsi_snapshot_take` would make it refuse exactly the databases it is for.
- **Resync checksums its candidate before believing it** (S-7). A terminator carries `spanlen`, so a candidate implies a span start, and that span can be verified. Skipping the check would make salvage a guess rather than a recovery, and everything it produced unverified while claiming otherwise.
- **Salvage never recovers a rolled-back span** (S-9), under any flag. Those records were deliberately aborted and no conforming reader has ever shown them.
- **A salvaged value may be an older one.** If a key's newest version was in lost bytes, salvage emits the newest that survives and reports the key as possibly stale (S-10). The report is the mitigation, so it must not be dropped as noise — and it needs no second pass, because files are scanned oldest first and positions ascend, so the first loss is discovered before any record beyond it is applied.

- **Reverse iteration is the same merge with the key comparison flipped — and ONLY the key** (D-14k). The generation tie-break stays newest-first in both directions, or step 3 would suppress the wrong duplicate and yield overwritten values. `ZS_FETCHPREV` is a throwaway reverse cursor exactly as `ZS_FETCHNEXT` is a forward one (D-14l, G-7): the fetch family is two shapes, not three, and predecessor lookup structurally cannot disagree with reverse iteration.
- **A reverse prefix scan seeks the prefix's byte-successor, never the prefix itself.** The largest key ≤ the prefix is BELOW every key carrying it (F-11a sorts the bare prefix first), so seeking the prefix reports a populated range empty. The successor — increment the last non-0xFF byte, truncate after it — is the least upper bound of the prefix range, and the seek at it must be EXCLUSIVE: the successor may exist as a real key. All-0xFF has no successor and correctly means "from the end", because every key above it carries it. Computed once at open into `c->rev_succ`, so a D-14j refresh re-derives the open's bound rather than trusting a stale arm.
- **A refresh re-seeks the transaction arm from the CURSOR's resume point, never from the arm's own position.** The arm's position is the last key consumed *from that arm*, which lags the merge — an arm exhausted at open has consumed nothing at all — so re-positioning it from its own state resurfaces any key stored into the gap, and the merge yields it BEHIND the last key returned. Found downstream (cyrus aaa-db `foreach_changes`): a key stored mid-walk at a position already passed came out of the traversal out of order, shifting everything after it by one. `zsi_cursor_reseek_arm` exists so the txn-only re-seek and the full re-seek share one resume rule; the mutant "cursor: txn arm resumes from its own position" is the bug preserved.
- **The pending set is a SKIPLIST, and the reason is not speed** (since 2026-08-16). It was one sorted array, which splices a key in with a `memmove` — so an ascending key landed at the end and moved nothing while a key arriving anywhere else moved half the array, making a transaction **quadratic in its distinct keys**: 0.19s ascending against 4.99s random for 200k records in one transaction, four times the time for twice the keys. No benchmark could see it, because every store workload wrote ascending keys (`store, all in one txn, random` exists now). `ZSI_DELTA_MAX`'s comment had described the same bug for the *read*-side index for months — "a single sorted array with no delta would memmove the entire index per commit" — and the pending set was that array. The base+delta shape that comment describes was the other candidate; a skiplist won for a reason that is not performance: **a node never moves, so a cursor's position is a POINTER**. All of D-14j-a existed because an array index stops referring to its record when an insert shifts the array, so the arm held a key, re-resolved it by binary search on every step, and cached the result behind two guards that no test could reach through a cursor. `struct zsi_fcur`'s transaction half is now one pointer, a step is `node->next[0]`, and a write cannot invalidate an arm at all. **Cost: −12% on the ascending bulk load** (1.74 → 1.54M records/s), which is the case the array was perfect for — a node `malloc` against an append into a slot that already existed. Level 0 is doubly linked because D-14k walks backwards. The level generator is seeded to a non-zero constant deliberately: **zero is a fixed point of xorshift**, and `zsi_zmalloc` leaves it there, which would give every node the maximum level — a correct skiplist that is a linear search.
- **`struct zs_txn`'s SIZE is on the read path, even though its contents are not.** `zs_db_begin_cursor` makes an implicit transaction, so every cursor allocates one — and growing it from 184 to 344 bytes for the skiplist cost **6.3%** on a scan that executes no pending-set code at all. `perf stat` is what identified it: +0.5% instructions, +15.7% cycles, IPC 2.31 → 2.01, **+9.4% data cache misses**, L1-icache flat. Same work, worse memory. The mechanism is the allocation crossing a malloc size class and shifting everything the merge loop touches afterwards; moving the 128-byte level-head array into the arena took it to 216 bytes and the regression went with it (5 of 5 paired rounds favouring the old build, by 4–8%, became 3 of 5 with overlapping ranges). Two lessons, and the second is the durable one: a field added to `zs_txn` is paid by every read cursor, and **an A/B on one machine's laptop cannot see this at all** — the same commits measured level under both clang and gcc-15 on an M5 while costing 6% on an EPYC.
- **The nodes live in ONE arena and link by OFFSET, the way Cyrus's skiplist file does** — and it works for the same reason it works on disk: an offset survives the arena moving, so the `realloc` that doubles it relocates every node at once and not one link needs fixing. That is what keeps the property the skiplist was chosen for: a raw pointer would be invalidated by the `realloc`, an offset is not, so a cursor's position is still stable across any write. The LEVEL HEADS live at the head of the arena, not in `struct zs_txn`: inline they were 128 bytes in every transaction, and a READ transaction never stores — `zs_db_begin_cursor` makes one implicitly, so every cursor was allocating and zeroing a pending set it could not use. With the arena allocated on first store, a read transaction has none at all, and `struct zs_txn` went 344 → 216 bytes. Key bytes are inlined after the level array — **up to a 64-byte bound, variable-length** — in the same cache line as the links that reached them, which is safe only because **nothing holds a pending key across a store** — every borrow is read inside the call that took it, and the cursor's D-14j-b resume key comes from a *record*, not from here. Worth **+2.5%** and two allocations per distinct key, not the 12% hoped: the remaining gap to the old array is the DESCENT, not allocation.
- **The inlined key is BOUNDED at 64 bytes, and the bound is a memory decision that costs throughput.** Inlining the whole key is faster nearly everywhere — measured against every alternative, it wins at 12, 41 and 200-byte keys in both key shapes and loses only above ~500 — but it makes an entry O(keylen), so a transaction holding a million 1200-byte message-ids is 1.2GB of pending set. Since values live in the file, the pending set *is* the transaction's footprint, so that is unbounded memory for a caller who cannot know their key sizes in advance. The bound caps an entry at ~112 bytes and costs **7.8% at 12-byte keys, 3.6% at 41, 2.5% at 200**, and *gains* 5% at 1000. **64, not 32**: a key at or under the bound is inlined WHOLE and decided without reading a record, and 64 covers sqlite's 12-byte rowid and 30–60 byte index keys, a `G`+40-random conversations key, and most mailbox names — where 32 left `Ndomain!user.foo` runs agreeing past the bound and measured 40% slower. **Variable-length, not a slot**: a 12-byte key costs 12 bytes (from the sqlite integration, where the distribution is sharply bimodal and a fixed slot would have been 5× the payload for the commonest record). Above the bound the prefix still decides unless two keys agree within 64 bytes, and only then is the record read — resuming PAST the bytes already known equal, or the fallback would cost strictly more than storing no prefix at all. Three things were measured and rejected: storing no key (−16 to −23%), a 32-byte bound, and a mixed mode that inlines whole keys under the bound and stores nothing above it (never best: it throws away the prefix exactly where it discriminates). `zsi_pend_cmp` is split so the at-or-under-bound case inlines into the descent — leaving them together was 10% at 12-byte keys, the zsi_cursor_refresh lesson again — and the descent loads each node ONCE for both its comparison and its link, which was another 2.5%. Measured at 100k records, medians of seven: array 1.697M/s, skiplist with a `malloc` per node 1.483M, arena 1.519M. And the cost is monotonic in transaction size — **zero at 10 records per transaction**, where the two commit gates swamp it, −5.5% at 100, −8.2% at 1000, −10.5% at 100k. A dual-mode structure switching at some size was considered and rejected: the win is 5–8% in a band already running at 1–2M records/s, against two implementations of lookup, seek, step, reverse step and the fold in the area this file records as having produced the subtlest bugs.
- **The active file's mapping is deliberately LARGER than the file, and `maplen > size` is normal.** A sole writer takes the D-13b fold at every commit (the refcount is 1 whenever nobody is reading), and that called `zsi_file_remap`, which unmapped and remapped the *whole* active file — growing toward `rollover_size`, so hundreds of pages torn down and refaulted per commit. Mapping once with headroom and then only moving the `size` bound costs no syscall at all, because the page cache is shared with the writing descriptor. Found by `perf record -e cache-misses` on an EPYC server: `find_vmap_area` alone was 12% of the profile and the mmap path about 20%, against a merge loop that did not appear at all. **What makes it safe is that `zsi_file_at` bounds every access by `size`, never by `maplen`** — reading into the headroom is SIGBUS — and that it is the single accessor, which was already true for F-30's reasons. `test_active_file_headroom_is_bounded_by_size` is the only place in the suite where the two bounds differ, so it is the only thing that can catch `file_at: bounds by the mapping, not the file`. The platform assumption — that an append through a separate descriptor shows up in a mapping made before it — is checked directly by `test_file_grows_under_an_oversized_map` rather than assumed.
- **`static inline` on `zsi_cur_order`, `zsi_ptrs_at` and `zsi_ptrs_rec` is a measurement, and `zsi_cursor_refresh` is split for the same reason.** Clang inlines all four into the merge loop at `-O2`; **GCC does not** — its auto-inline budget is far tighter, and each is called from more than one site — so a GCC profile of a full scan shows call frames a clang profile has no symbol for at all: `zsi_cursor_refresh` 4.7%, `zsi_cur_order` 3.6%, `zsi_ptrs_rec` 2.1%, `zsi_ptrs_at` 1.9%, about **12% of samples** spent calling into a comparison and two loads, per record. Saying `inline` moves them to `max-inline-insns-single` and GCC takes them: **+8.8%** on a four-file scan and +8.0% compacted, flat on clang. It must be said in the *source* — `zeroskip.c` is vendored, so it is compiled with the host project's flags and an inlining decision that matters cannot live in our `CFLAGS`. **No test can see any of this**, which is why it is written down: deleting the keyword is a silent 8% on every GCC build. The split is the same trick where a function is too big to inline — the "has anything changed" gate is inlined, `zsi_cursor_refresh_slow` is not — and its hazard is real: the gate decides `txn_moved` and `look` and the slow half re-derives **neither**, because two halves that disagree are a cursor that silently stops refreshing (G-4). That single-home rule is also what keeps the D-14j mutants aimed at reachable code; a mutation of a test the gate has already made would sit behind it as dead code and read as NOT CAUGHT. Found by `perf record` on the EPYC, on a `--run`-phase profile.
- **`zsbench`'s `full scan` does not measure a merge, and `full scan, interleaved` / `full scan, shadowed` exist because of it.** Keys are stored in ascending order, so every generation — and every repack output built from them — holds a contiguous key range no other file touches (measured: four files ending at key00131071, 00196607, 00198655, 00199679). One arm is live and the rest sit on first keys above everything being yielded, so D-14i-a's shortcut declines to move on every step but the three file boundaries and the duplicate scan breaks on its first comparison every time. The ~30% that line gives up against the compacted one is arm-array stride and one extra comparison per record, not merge work. **Anything aimed at `zsi_cur_resort_head`, `zsi_cur_order` or the arm layout must be measured against the two new lines** — interleaved is −22% against `full scan` and shadowed −40%, so the machinery costs about 40% when it is used and roughly nothing on the workload that was being profiled. This is the second time a benchmark's *shape* hid what it claimed to measure (the first: every store workload starting from an empty directory, which is why `store into N files` exists).
- **`zsi_cur_resort_head` returns after ONE comparison when nothing moves** (D-14i-a). The naive insertion sort lifts `c->cur[0]` into a local and puts it back whatever happens — and an arm is 160 bytes, so a step that moved nothing still copied 320 bytes, on every record of every scan. D-14i already said the advanced arm usually stays at the front; this makes that the cheap path instead of the expensive one. The failure mode is the shortcut being taken when the arm *should* have moved, which mis-sorts the array and yields out of key order silently — so `test_cursor_resort_no_move` runs **interleaved** files, where the head changes at every step and the shortcut must decline every time, as well as the dominant-file shape where it always applies. **`zsi_cur_sort` carries the same guard**, added later for the same reason found the same way: step 3 calls the full sort on every step of a scan whose keys are duplicated across files, and until `full scan, shadowed` existed nothing measured that shape — it was 10.3% of an EPYC profile, and the guard is worth **+11%** on that line and nothing on the others, since disjoint files never reach it.
- **The "last arm standing" case needs no machinery: it is already free.** Once every other arm is exhausted, `zsi_cur_order` returns on `b->exhausted` before reaching the comparator, and step 3's duplicate loop breaks on the same test. Worth knowing before building run detection for it.
- **`struct zsi_fcur`'s position fields are a UNION, and that is a size decision, not a tidiness one.** `c->cur` is an array the merge walks twice per record (arm 0 to yield, arm 1 to compare), so every byte of an arm is stride for the next. `kind` already discriminates the halves, so unioning costs max() rather than sum() — and since the transaction half became a single node pointer it is the FILE half (`pi`, `ic` — 24 bytes) that sets the size. **128 bytes**, down from 160 when the transaction half was six fields and 168 before the step hint that is now gone entirely. The cost of the extra name (`fc->u.f.pi`, `fc->u.t.node`) is 60 call sites and worth paying once.
- **`struct zsi_fcur` is what the merge loop walks, and its size is measurable.** A since-deleted step hint took it 168 → 200 bytes at one point, and trimming it to 184 was worth about **4%** on a multi-file scan against 184 bytes, about 13% against 200 — small, and *below the ±10% run-to-run noise* the same benchmark shows at smaller sizes, so it is only visible at `-n 500000` upward. The union above is what recovered it. The lesson worth keeping is the measurement one: a laptop A/B could not resolve the effect at all until the sample size grew, and two hours went into chasing a number that `perf stat -e cache-misses` would have settled in one run.
- **What survives of D-14j-a is at the CURSOR level, and it is the part that always mattered**: a refresh re-seeks the transaction arm from the CURSOR's resume key, never from the arm's own position (`zsi_cursor_reseek_arm`). The arm reads one record *ahead* of what the caller has seen, so a write landing between the last key yielded and where the arm sits must still be picked up — that is a rule about the merge, not about the data structure, and it outlived the array that motivated it. The bug it preserves (`cursor: txn arm resumes from its own position`) was reported from the Cyrus integration and was silent: the traversal processed a record twice.
- **`struct zsi_fcur` owns nothing** (since 2026-08-15). It used to be a `malloc` + `memcpy` + `free` per step, the same waste as the cursor's resume key. Three independent things make the borrow safe, and it is worth knowing which is which. The weakest and most quotable: **`zsi_pend_set` allocates each key once** — an insert `memmove`s the ENTRIES and may `realloc` the array, an overwrite repoints `off`/`len`, and neither moves a key block; they are freed only by `zsi_pend_clear` from `zsi_txn_free`. Stronger, and what actually carries: **the arm's two borrowed pointers are only ever READ inside a seek/next → load chain that just wrote them**, with no caller code in between — and any write to the transaction bumps `pend_seq`, so the next step refreshes and `zsi_cursor_reseek_arm` re-seeks the arm from the CURSOR's `last_key`, overwriting both before either is read. That is why the `pend: reallocates the key block on overwrite` mutant is `equivalent` and not a gap; it was verified under ASan on a scratch copy, not assumed. `zsi_fcur_fini` is now empty and is deliberately still called from all six sites.
- **The arm reads one record AHEAD of what the caller is looking at.** D-14e step 5 advances element 0 *before* the record is handed over, so inside a `foreach` callback on key *n* the transaction arm is already positioned on *n+1* and it is *n+1*'s pending key it holds a pointer to. Any test aiming at the arm's borrowed position has to write to the key after the one it was just given; `test_txn_cursor_survives_pending_array_growth` does both, and aiming only at the current key is why an earlier version of it proved nothing.
- **A cursor's per-file hold is redundant; a READ TRANSACTION's is not.** Both were `catch` mutants and the cursor's had never been caught at any commit. Every job it does is covered elsewhere in every reachable configuration: A-4a retention by `zsi_snapshot_retire` at each live swap (and by `db->snap` before any swap), and the commit-site fold guard by the transaction the cursor always sits inside — `zs_db_begin_cursor` makes an implicit read transaction, which holds. The one case where the cursor's hold stands alone is a cursor on a *write* transaction, which owns the write lock so no commit can run underneath it. The transaction's hold *is* load-bearing, in the configuration nothing tested: **a read transaction with no cursor**, where the snapshot reference keeps the bytes alive but only the hold raises the file refcount that stops the fold mutating the active file in place — which would let a fixed view see a later commit (G-4). `test_read_txn_view_is_fixed_without_a_cursor` is that case.
- **A leak is not a test failure, so `make leaks` catches things `mutate.sh` cannot.** `hold: references never released` went NOT CAUGHT for the life of the suite for exactly that reason. `test_hold_releases_its_references` turns it into one by counting `/dev/fd` across 60 transactions interleaved with commits — the commits matter, since a snapshot rebuild is the only thing that retires a file and so the only way a missing release becomes observable.
- **The refcount is on the FILE, not the snapshot** (A-4a, C-4c-a). A snapshot is only one user of a file; a transaction or cursor holding returned pointers is another. `zsi_snapshot_retire` takes a reference per file into the borrower's `zsi_hold`, released at `zsi_hold_fini` when the transaction or cursor ends — that is the first moment the bytes may go. Counting on the snapshot instead is how two bugs shipped in one week, and both read as sound reasoning: *"someone else still holds the snapshot, so the bytes are safe"* (they outlive us only by assumption — a cursor does not: fetch, open a cursor, store, close the cursor, and the transaction's borrow is unmapped), and *"the snapshot's refcount tells me whether anyone is reading the active file"*, which is what the D-13b fold guard used to ask. It now asks `act->refcount == 1`, the actual question.
- **A cursor and a READ transaction reference every file in their snapshot; a WRITE transaction does not.** The references do two jobs at once: A-4a retention, and telling the commit-site fold that somebody is reading the active file so it rebuilds instead of mutating in place (G-6, G-4). A write transaction is excluded because it is the one doing the folding — its own reference would be indistinguishable from a reader's and would disable the incremental path entirely, which is the quadratic bulk load D-13b exists to prevent. Its borrows are safe regardless, because the fold happens during commit and commit ends the transaction's A-4 lifetime.
- **Immutable files are SHARED between snapshots, and the active file never is** (C-4c-a). `zsi_fcache` carries already-opened, already-indexed files across a rebuild, keyed on the filename — sound because generations are never reissued (D-9b, D-9c) so a name identifies its bytes for the life of the database. Measured: a rebuilding begin went from 171µs to 46µs at 10 files, 565µs to 74µs at 40, and 1576µs to 171µs at 120 — the per-file cost drops from ~13µs to ~1.1µs. The active file is excluded because its index and `complete` boundary belong to the *snapshot* that built them; caching it lets an older snapshot see records committed after it was taken, and `test_txn_cursor_view_is_fixed` catches that immediately. The exclusion is stated once, at the `put`, deliberately: guarding the `get` as well would leave neither statement testable, since defeating either alone changes nothing.
- **A cursor takes its own snapshot reference.** It used to borrow the transaction's, which was fine while a cursor's snapshot never changed; D-14j lets a handle-live cursor swap to a newer one, and releasing a borrowed reference frees a snapshot the transaction still points at.
- **A cursor's D-14j-b resume key is BORROWED from the record it yielded, not copied** (since 2026-08-14). Copying it looks like the careful choice and is dead weight: A-4 already promises the *caller* those exact bytes for the whole cursor, and the resume point needs them only until the next step — so if the copy were load-bearing, the record the caller is holding would be dangling too. `c->emitted` two lines above has always taken the same borrow, and `zs_cursor_replace` dereferences it arbitrarily later. `ZS_EPHEMERAL` is the one place A-4 is weakened (A-4b) and cannot reach it: the public cursor and `foreach` forms reject the flag, so the only source that sets it belongs to the throwaway `ZS_FETCHNEXT`/`ZS_FETCHPREV` cursor, which takes a single step and is freed inside the call — a second step is the only thing that reads the resume key. Worth 37.3M to 53.0M records/s on `zsbench`'s full scan (80.6M compacted), because it was a `malloc` + `memcpy` + `free` on *every record*.
- **What keeps that borrow alive is the hold, and the ACTIVE FILE is what makes it observable.** C-4c shares immutable files across snapshots, so an ordinary swap hands the same object back and retires nothing — which is why every pre-existing D-14j test would pass whether the borrow were sound or not. The active file is excluded from that cache (its index and `complete` boundary belong to the snapshot that built them), so a handle-live swap over a live active file *always* retires the object the resume key points into, and only `zsi_hold` keeps it mapped. `test_cursor_resume_key_survives_retirement` is that case; the mutant is `hold: takes no references at all`, which segfaults.
- **`zsi_snapshot_retire` at the cursor's live swap is redundant, and the mutant for it is `equivalent`.** `zsi_hold_add_snapshot` does not dedup and the cursor calls it on every snapshot that becomes `c->snap` — at open, and again at the end of each swap — so the outgoing snapshot's files are already held by the time the retire runs. A write transaction holds only when `ZS_SHARED`, so *its* retire is the only reference and its mutant does bite. The asymmetry is the thing to remember before removing either hold.
- **`c->handle_live` cannot be derived from `c->txn`.** A read-only implicit transaction is passed to the cursor as NULL, so the `zs_db_*` wrapper that created it has to say so — which is why `struct zs_txn` carries `implicit`.

## Testing

Tests use a custom harness with `ASSERT()`, `ASSERT_EQ()`, `ASSERT_EQU()`, `ASSERT_OK()`, `ASSERT_SIGN()`, `ASSERT_STR_EQ()`, `ASSERT_MEM_EQ()`, and `CB_`-prefixed variants for callbacks. Each test gets a fresh temp directory via `setup()`/`teardown()`; `basedir` exists, `dbdir` deliberately does not, so tests exercise `ZS_CREATE`.

`tests/corpus/` is **language-neutral by design** (T-0) — data files plus a portable text description, not fixtures in C source. `make corpus` exists to add cases, not to paper over a diff: if it changes an existing case's bytes, that is a format change and needs a spec commit.

### `make mutate`

`tests/mutate.sh` introduces, one at a time, the specific bugs the suite claims to guard against, and reports whether the suite noticed. Add a mutant whenever you add a test for a requirement — a test that passes but cannot fail reads as coverage while providing none.

It has already earned this: it found that several header tests passed under a *symmetric* layout change (swap the `start` and `end` offsets and a matched encoder/decoder round-trips perfectly), which is exactly the bug class that makes another implementation unable to read our files. `test_header_byte_layout` exists because of that finding, asserting the 72 bytes against a literal.

Two mutants are marked `equivalent` rather than expected-to-be-caught, because they genuinely do not change behaviour: delegating the comparator's prefix compare to `memcmp`, and dropping `roundup8`'s overflow guard. They are listed so nobody writes a bogus test chasing them. If you find a mutant that *should* be equivalent but gets caught, the classification is wrong — investigate rather than reclassifying.

The perl patterns are tied to exact source text and will rot when the code is refactored. The script reports `PATTERN ROTTED` rather than silently passing; fix the pattern, don't delete the mutant.

**A COMPOUND pattern can half-rot, and `--rot-only` calls it intact.** A mutant with two substitutions applies whichever halves still match, so when a refactor deletes what one half targeted, the other half applies alone — usually producing something harmless, which then reads as NOT CAUGHT. `--rot-only` reports the pattern intact because it matches *at all*. It happened to `txn arm: hint stamped at the step, not the load` the moment the hint stopped being stored in its own fields. Prefer one substitution per mutant; when two are genuinely needed, a NOT CAUGHT verdict means "check both halves landed" before it means "write a test".

**`--rot-only` proves a pattern MATCHES, not that the result COMPILES.** A mutant naming a function since renamed, or a variable the code no longer has, still matches and still reports intact — then reports `BUILD FAILED (inconclusive)` in a full run, which is to say it has been testing nothing while looking like a line item. Three were in that state when `--build-only` was added, two of them long-standing (`zsi_file_close` has not existed for years; the function is `zsi_file_release`). **`./tests/mutate.sh --build-only`** applies and compiles every pattern without running anything: 3m19s against ~50 minutes for the full verdict, so it belongs in the same reflex as `--rot-only` after touching `zeroskip.c`.

**"Fixing" a flaky test can silently remove its power, and that is worse than the flake.** `test_salvage_active_file_is_newest` depended on byte arithmetic — whether the loop's last commit crossed `rollover_size` — and started failing when records got 4 bytes shorter. The repair re-stored *the same* value until an active file existed, which put that value in both the sealed file and the next active one, so the ordering the test exists to pin stopped mattering. It passed, and `salvage: active file sorts first, not last` went from caught to NOT CAUGHT with nothing in the library changing. The retry now writes a **distinct** value per attempt. When a test is made robust, re-run its mutant: robustness and discrimination are different properties and the repair traded one for the other.

**A pattern can match the WRONG site and still report intact.** `mutate.sh` applies `perl -0pi -e 's///'` with no `/g`, so it replaces the *first* match — and a refactor that introduces an identical line earlier in the file silently retargets the mutant onto it. `--rot-only` cannot see this, because the pattern still matches something. The symptom is a mutant reporting `NOT CAUGHT`, which reads as a test gap and is really a mis-aimed mutation; it happened to `salvage: processes newest first` the moment `zsi_entry_resolve_order` gained a comparison line identical to `zsi_salvage_order`'s. When a mutant you believe in reports NOT CAUGHT, check *where* the pattern landed before writing a test to chase it, and anchor on something unique to the function when the statement alone is not.

**The full run costs about an hour, so it is affordable per release.** 300 mutants took **55 minutes** on an M5 laptop — roughly 11 seconds each, a rebuild plus both test binaries. Treat published estimates here with suspicion: this note has said "several hours" and "an overnight job" at various points, and each figure was measured on a different machine or a smaller suite, so the number drifts in both directions. Time it rather than trusting the note. Day to day: run the mutants you are adding by name (`./tests/mutate.sh <substring>`), and `./tests/mutate.sh --rot-only` after refactoring `zeroskip.c` — it applies every pattern with no build and no run, so pattern rot (the thing that silently accumulates between full runs) is checked in seconds.

**`mutate.sh` snapshots the sources into a temp directory and mutates the copy.** The checkout is never written, an interrupted run cannot leave a mutant in the tree, and concurrent runs each have their own copy. It used to mutate `zeroskip.c` in place, and every failure mode that design permits actually happened: a concurrent edit silently reverted, two overlapping runs corrupting each other's verdicts — and a stale run from an interrupted session that sat parked on a stopped child for days, holding a pre-fix backup it would have restored over the repo the moment it advanced. The flip side of the snapshot: edits made to the repo after a run starts are not part of that run's verdict, so re-run after changing anything.

**Killing a `mutate.sh` run still orphans stopped `zstest` children.** It sets `set +m`, so the fork-based tests' children are left in `T` state rather than reaped, and they survive for hours holding descriptors. They cost no CPU, so the symptom is not an obvious hang but an inexplicably slow machine much later. After interrupting a run: `pkill -9 -f '^\./zstest'`, and check `ps aux | grep zstest` before blaming anything else for being slow. A killed run's mutant `zstest` binaries stay in its temp directory, not in the repo — the repo binaries are whatever they were before the run.

**A test must not be able to damage `tests/corpus/`.** `test_corpus_index_table` originally pointed a live cache directory at the checked-in corpus, and since a cache directory is one the library *unlinks from* (P-16), the two `sweeps` mutants deleted the golden table outright — which then made five unrelated mutants read as caught. It copies the case to scratch first. A deleted corpus file reads like a corpus that needs regenerating, which is exactly the diff `make corpus` must never be used to resolve.

## Interoperability surface

Changing any of these breaks other implementations, so they need a spec change first:

- the 16 magic bytes, the 72-byte header layout, the 10 type bytes, the record and terminator layouts, the pointer section and its 16-byte trailer
- XXH3-64 with seed 0, truncated to the low 32 bits, little-endian
- the default comparator's total order and the exact bytes of the `memcmp` name field
- filename format: lowercase hyphenated UUID, uppercase 8-digit hex generations, **no extension** (D-1a — the unordered name must sort before the in-order name for the same generation)
- `fcntl` record locking on `zeroskip.lock` bytes 0/1/2
- the pointer table's 16 magic bytes, its 96-byte header layout, the offset array
  and its trailing checksum, and the `zeroskip.index-<uuid>-<GEN8hex>` name —
  located at `<cache root>/<uuid>/` for a configured root (P-2a), or directly in
  `zeroskip.cache/` inside the database directory under `ZS_INDEX_LOCAL` (P-2b)
- `zstool --hex`'s line format, which the interop runner compares as text (the raw default is for humans, and is not interop surface)

Locks are ordered *within* one database. A caller holding locks on several databases while writing must impose its own consistent order (C-1h).
