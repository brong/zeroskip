# Salvage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `zs_db_salvage(from, to, setup)` rebuilds whatever is readable out of a damaged database directory into a fresh one, without ever writing to the source.

**Architecture:** A new `SALVAGE` section at the bottom of `zeroskip.c`, below `PUBLIC API`. It deliberately does **not** share the read path: the whole point is reading structures the normal path refuses — a set that does not tile, a file whose header fails, a pointer section that does not load, spans after a bad one. It scans, and writes through the ordinary public write path into the destination.

**Tech Stack:** C99, POSIX, no external libraries.

**Design doc:** `docs/superpowers/specs/2026-08-07-seal-compact-salvage-design.md`, section C. Sections A and B are already implemented.

## Global Constraints

- **The spec is normative.** Spec changes land in their own commit, *before* the code (Task 1).
- **Salvage MUST NOT write to the source.** Open it read-only, never take its lock, never unlink from it. That is what lets salvage guess and improvise at all, and it is the property every test must be able to demonstrate.
- **Every recovered byte is checksum-verified by default.** Only `ZS_SALVAGE_UNVERIFIED` relaxes that, and everything it recovers is reported.
- **Rolled-back spans are never recovered**, under any flag (F-21, F-25).
- Sections in `zeroskip.c` may only call **upwards**. `SALVAGE` goes last so it may use everything.
- Internals are `static` with a `zsi_` prefix; every function returns `enum zs_ret`.
- `make asan` and `make leaks` clean first; a bare `make check` after `make asan` runs the *sanitizer* binary.
- **Nothing may touch `zeroskip.c` while `tests/mutate.sh` runs**, and two runs must never overlap.
- Slow suites (`asan`, `leaks`, `bench`, `mutate.sh`) are batched at the end, not run per task. During development run `make zstest && ./zstest <filter>`.
- Commit messages end with `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`.

- [ ] **Step 2: Write §9**

```markdown
## 9. Salvage

Recovery of what is readable from a damaged directory. Everything here is
OPTIONAL: an implementation that does not offer salvage is fully conforming.
What is normative is what an implementation that *does* offer it must and must
not do, because a salvage tool that silently invents data is worse than none.

- **S-1** Salvage reads a source directory and writes a **new** database
  elsewhere. It MUST NOT write to the source, take any lock on it, or unlink
  anything in it. That is what lets it read structures §5's rules refuse.
- **S-2** Salvage MUST NOT apply D-5's overlap resolution or D-6's tiling check.
  A gap is reported and stepped over. One missing generation makes a database
  unopenable by §7's rules while every surviving file remains perfectly
  readable, and recovering those is the point.
- **S-3** Files are processed oldest first: by `start` ascending, and for equal
  `start` the narrower range first, since a wider one is a repack output derived
  from it. Records are applied in that order, so the newest surviving version of
  each key wins by construction and no separate recency pass is needed (D-14).
- **S-4** The source's comparator does not affect the output. The output is
  ordered by the comparator the caller supplies, and recency is resolved by
  generation and offset. Where a source header is readable its comparator name
  MUST be compared against the caller's and a mismatch reported; where no header
  is readable there is nothing to check.
- **S-5** A file whose header does not validate is still processed. Its
  generation comes from its filename (D-1). Its checksum engine is determined by
  trying each in turn and keeping the one under which a span validates; engine 0
  matches only where the stored checksum really is zero, so it is a genuine
  signal rather than a catch-all. Both facts MUST be reported.
- **S-6** For an in-order file the pointer section MUST be ignored and the
  records region walked directly. A pointer section that fails to load makes the
  file unreadable under §7 while its records may be intact, and an in-order file
  has no spans (F-23), so the walk is a flat record walk.
- **S-7 Resynchronisation.** On reaching a span that does not validate, salvage
  MUST attempt to resynchronise rather than stopping as F-24 requires of a
  reader. From the failed position, step forward in 8-byte increments (F-2) and
  attempt to decode a terminator at each. On success compute
  `span_start = position - spanlen`; if that lands at or after the last known
  good boundary, checksum `[span_start, position)` together with the
  terminator's own bytes and compare against the terminator's stored checksum. A
  match is a **verified** span and the walk resumes from it.

  This is what makes the default sound: everything recovered after damage is
  checksum-verified, not merely decodable. Today one bad span discards every
  later span in its generation (F-24), and those spans are exactly what this
  recovers.
- **S-8** The span that failed cannot be verified — its terminator is what would
  prove it — and neither can a trailing region with no valid terminator. Their
  records MUST NOT be recovered unless explicitly requested, and every record so
  recovered MUST be reported. These records carry no checksum of their own:
  F-19's terminator checksum is the only thing that ever covered them.
- **S-9** A **rolled-back** span MUST NOT be recovered under any option. F-21
  and F-25 make it deliberately aborted, and no conforming reader has ever shown
  its records.
- **S-10** Salvage MUST report, per key, where the record it recovered may be
  stale: where that record is older than some point at which data was lost, a
  newer version may have been in the lost bytes. A key whose winning record is
  newer than every damage point MUST NOT be reported, so the report stays small
  enough to act on.
- **S-11** Reporting is structured — a kind, a location, and a key where one
  applies — not prose. S-10's report is the mitigation for emitting a possibly
  stale value, so it must be machine-readable rather than something a human has
  to parse back out of a message.
- **S-12** Salvage MUST NOT reconstruct a missing generation's contents, invent
  records, or repair the source. There is no in-place repair anywhere in this
  format (R-4), and salvage is not an exception to it — it is the reason one is
  not needed.
```

## Task 2: Public types

**Files:** `zeroskip.h`

**Interfaces produced:** exactly the API in the design doc's section C. Copy it
verbatim rather than paraphrasing:

```c
enum zs_salvage_kind {
    ZS_SALVAGE_FILE_UNREADABLE,   /* could not be opened or mapped */
    ZS_SALVAGE_HEADER_INVALID,    /* generation taken from the filename */
    ZS_SALVAGE_ENGINE_GUESSED,    /* which engine the spans validated under */
    ZS_SALVAGE_GAP,               /* a generation range absent from the set */
    ZS_SALVAGE_PTRS_IGNORED,      /* pointer section unusable; order rescanned */
    ZS_SALVAGE_SPAN_LOST,         /* a span that could not be verified */
    ZS_SALVAGE_SPAN_ROLLBACK,     /* deliberately aborted; not recovered */
    ZS_SALVAGE_RESYNC,            /* a verified span found after damage */
    ZS_SALVAGE_KEY_UNVERIFIED,    /* value came from an unverifiable span */
    ZS_SALVAGE_KEY_MAYBE_STALE    /* a newer version may have been in lost bytes */
};

struct zs_salvage_event {
    int          kind;
    const char  *file;        /* data file name, or NULL */
    uint32_t     generation;
    size_t       offset;      /* byte offset within that file */
    size_t       length;      /* bytes affected */
    const char  *key;         /* per-key events only */
    size_t       keylen;
};

typedef int zs_salvage_cb(void *rock, const struct zs_salvage_event *ev);

struct zs_salvage_data {
    uint32_t        flags;         /* ZS_SALVAGE_UNVERIFIED */
    zs_compar      *compar;
    const char     *compar_name;
    zs_csum        *csum;
    zs_salvage_cb  *report;
    void           *rock;
    void          (*error)(const char *msg, const char *fmt, ...);
};

#define ZS_SALVAGE_DATA_INITIALIZER { 0, NULL, NULL, NULL, NULL, NULL, NULL }

int zs_db_salvage(const char *from, const char *to,
                  struct zs_salvage_data *setup);
```

`ZS_SALVAGE_UNVERIFIED` joins `enum zs_flagspec` at a free bit — `1<<17` is next
after `ZS_CURSOR_PREFIX`. Check nothing else uses it:
`grep -n '1<<1[5-9]' zeroskip.h`.

## Task 3: The scanner

**Files:** `zeroskip.c` (new `SALVAGE` section), `zstest.c`

- [ ] **Step 1: Resynchronisation, tested directly**

The single most important piece, and the only place salvage guesses. Test it
against a hand-built file before wiring anything else up: three spans, the middle
one's terminator checksum corrupted, and assert that a walk from the failure
point finds the third span and verifies it.

Use the existing `ib_*` in-order builder or `put_unordered_kv` helpers —
`grep -n 'static void ib_init\|put_unordered_kv' zstest.c` — rather than writing
a new file builder.

```c
/* S-7: a bad span mid-file must not cost the spans after it.  The stored
 * spanlen is what makes this sound rather than a guess: it names where the span
 * began, so the candidate can be CHECKSUMMED before being believed. */
static void test_salvage_resyncs_after_a_bad_span(void)
```

Assert three things, not one: the third span is found; its recovered records are
correct; and a *corrupted* candidate is rejected rather than accepted (flip a
byte inside the third span too, and check resync moves past it rather than
returning it).

- [ ] **Step 2: The engine trial (S-5)**

```c
/* S-5: an unreadable header does not make a file unreadable.  Engine 0 matches
 * only where the stored checksum really is zero, so trying it last is a genuine
 * signal rather than a catch-all that would accept anything. */
static void test_salvage_invalid_header(void)
```

Build a database under engine 1, destroy its header bytes, salvage, assert the
records come back and that both `HEADER_INVALID` and `ENGINE_GUESSED` were
reported with the right generation.

- [ ] **Step 3: The whole-directory walk (S-2, S-3, S-6)**

`readdir`, parse names, sort per S-3, process each file, apply records oldest to
newest into the destination through `zs_db_store` / `zs_db_delete` in batched
transactions.

Tests:
- `salvage_across_a_missing_generation` — build several generations, delete a
  middle file outright, assert the source will not open at all
  (`zs_db_open` returns `ZS_AGAIN`), and that salvage recovers every key from the
  surviving files and reports one `GAP`.
- `salvage_newest_version_wins` — the same key written in three generations;
  assert the newest value survives.
- `salvage_ignores_pointer_section` — corrupt an in-order file's pointer section
  so `zs_db_open` fails, and assert salvage still recovers its records and
  reports `PTRS_IGNORED`.

- [ ] **Step 4: Rollback and unverified (S-8, S-9)**

`test_dump_shows_rollback` already hand-builds a ROLLBACK span — reuse that
construction. Assert its records are absent both with and without
`ZS_SALVAGE_UNVERIFIED`, and that a trailing torn tail is absent by default and
present with the flag, reported as `KEY_UNVERIFIED`.

- [ ] **Step 5: Stale detection (S-10)**

Track the earliest damage point per file as `(generation, offset)`. After the
scan, a key is `KEY_MAYBE_STALE` if the record that won for it is older than any
damage point.

```c
/* S-10: only keys that COULD have been superseded by lost bytes are reported,
 * so the report stays small enough to act on.  Asserted both ways: a key whose
 * winning record is newer than all damage must NOT appear. */
static void test_salvage_reports_maybe_stale(void)
```

- [ ] **Step 6: The source is never written (S-1, S-12)**

The property everything else rests on.

```c
/* S-1, S-12: salvage never writes the source.  Asserted by content, not by
 * intent: every file's bytes and mtime are captured before and compared after,
 * and the lock file must not appear if it was absent. */
static void test_salvage_never_writes_the_source(void)
```

Also assert salvage works on a source directory made **read-only**
(`chmod 0500`), which is the strongest form of the same claim — and skip that
part when running as root, where the mode is not enforced.

## Task 6: Documentation

**Files:** `doc/overview.md`, `CLAUDE.md`

- [ ] **Step 1: Prose**

`doc/overview.md`: what salvage recovers and what it cannot, in plain language,
including that a recovered value may be an older one and that the report says

`CLAUDE.md`, under *things that look like bugs and are not*:

```markdown
- **Salvage does not share the read path, and must not.** It exists to read what §5 and §7 refuse — a set that does not tile, a header that fails, a pointer section that will not load, spans after a bad one. Routing it through the normal path would make it refuse exactly the databases it is for.
- **Resync checksums its candidate before believing it** (S-7). A terminator carries `spanlen`, so a candidate implies a span start, and that span can be verified. Skipping the check would make salvage a guess rather than a recovery, and everything it produced unverified.
- **Salvage never recovers a rolled-back span** (S-9), under any flag. Those records were deliberately aborted and no conforming reader has ever shown them; recovering them would resurrect a transaction that did not happen.
- **A recovered value may be an older one.** If a key's newest version was in lost bytes, salvage emits the newest that survives and reports the key as possibly stale (S-10). That is the trade "recover as much as possible" asks for, and the report is the mitigation, so it must not be dropped as noise.
```

## Self-review notes

**Spec coverage.** S-1 to S-12 each have a test in Task 3 and a conformance row
in Task 1.

**Known soft spots, flagged rather than hidden:**

- Task 3 Step 1 depends on which file-building helpers `zstest.c` already has;
  the plan says to find them rather than specifying a new one, because writing a
  builder blind would duplicate what is there.
- The resync scan is O(file size / 8) candidate positions, each an O(1) decode
  plus, on a decode hit, one checksum. Worst case on a 2 MB file that is 256 K
  decodes. Acceptable for a recovery tool run rarely; **measure it** before
  claiming it is fine, and if it is not, the fix is to require the candidate's
  implied `span_start` to be the last known boundary before checksumming.
- S-10's staleness rule is conservative: it reports any key older than any damage
  point, which over-reports when the damage was in an unrelated key range. Making
  it exact would need the lost bytes' key set, which is precisely what is lost.
  Say so in the docs rather than implying the report is tight.
- Deciding `ZS_SALVAGE_UNVERIFIED`'s bit requires checking the flag space; the
  plan says to grep rather than asserting `1<<17` is free.
